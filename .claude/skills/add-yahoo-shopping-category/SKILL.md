# Yahoo!ショッピング商品ランキング型カテゴリーの追加

> **2026-10-03 改訂**: シュレッダー・プリンター・発電機の追加で得た知見を反映した。旧版の「APIルート/ページを projector からコピーする」手順は廃止済み(現在は共通の動的ルート+薄いラッパー)。ページ側の拡張機能(STEP選択・説明つき広告セクション・ブランド導線・取得件数の設定)は `commerce-page-design` スキルを参照。

## Why this skill exists

The `projector`(会議用プロジェクター) category took a full session of iteration to get right: filters that turned out to be useless were built then removed, a scoring calibration bug silently neutered a 50%-weighted ranking factor, an Astro CSS-scoping bug meant product cards had zero styling for a while, and several correctness bugs around delivery-date handling and duplicate listings were found and fixed one at a time. All of that is now captured as the reusable pattern below. Rebuilding a new category from a blank page would silently reintroduce every one of those bugs. Follow this skill instead of designing from scratch.

Full narrative background (why each decision was made) is in the memory file `project_yahoo_shopping_affiliate_pattern.md` (in this Claude Code installation's memory store for this project) — read it if you want the reasoning, not just the recipe.

## Step 0 — 作る前に候補を評価する(2026-10-04 追加)

候補が複数ある、または報酬の見込みが分からないときは、設定を書く前に `scripts/profile_category.cjs --queries "<語>"` を1回実行する(API 1〜3回)。総ヒット数、想定報酬の分布と「足切り額ごとに残る割合」、ジャンル、ブランド、商品名の頻出語、名前サンプルが一覧で出る。ユーザーに「次のカテゴリー」を選んでもらう場面では、候補ごとの特性を実測で添えると選びやすい。

見極めの目安(実測):
- **低報酬カテゴリー**: 500円以上の商品が1割未満(ホワイトボード 303件中8件、シュレッダーは3%)。足切り(`minEstimatedCommission`)を50〜200円に下げないと成立しない。標準の500円のままだと件数が半減以下になる。
- **大型・重量物**(ホワイトボード・オフィスデスク/書庫): 東京宛ての「翌々日まで」と判定される商品が少なく、足切りなしでも約84件(ホワイトボード)。FAQ に「大型の商品は地域によって翌日到着の対象にならない場合がある」旨を入れる。
- **ブランド**: `brand.name` がストアブランド(オフィスコム・LOOKIT 等)や「ブランド登録なし」ばかりなら、ブランドセクションは付けない(`add-popular-brand-section` の「付けない判断」を参照)。
- **範囲の重なり**: 既存カテゴリーと重なる商品(例: オフィスデスク・書庫の検索結果に出るオフィスチェア = 既存の office-chair)は除外語に入れる。

## Before you start: confirm scope with the user

Ask (briefly, not a whole form) for:
- **slug** (URL-safe, English, e.g. `orchid`)
- **display name** (Japanese, e.g. `胡蝶蘭`)
- **2-4 search queries** to send to Yahoo (e.g. `["法人 胡蝶蘭", "開店祝い 胡蝶蘭", "取引先 胡蝶蘭"]`) — these are fixed server-side queries, never user input
- **a required keyword** (or a couple) that must appear in the product name for a hit to be relevant at all — this is the single biggest lever against irrelevant results, so pick something specific (for projector it was just `"プロジェクター"`)
- roughly what "arrives fast" needs to mean for this product (usually still 明日まで/翌々日まで — see below, this basically never changes)

ユーザーが「次のカテゴリを追加して」とだけ言って候補を指定していない場合は、推測で決めずに AskUserQuestion で候補(2〜4個)を提示して選んでもらう。カテゴリーが決まっている場合の検索語・必須語は、下の Step 1 の実測で決めて報告時に根拠を示せばよく、毎回ユーザーに聞く必要はない(シュレッダー・プリンターはこの進め方で追加した)。

Don't guess these — a wrong required-keyword or query list produces a page full of irrelevant products and you won't necessarily notice until you look closely, because the ranking will still confidently sort garbage.

**If the user picked this category because they expect it to be high-commission, sample brand names too, not just the generic category name.** `office-chair`'s generic queries (`オフィスチェア`/`デスクチェア`/`ワークチェア`) returned a perfectly clean sample with zero noise — but a median commission of only ~118円, because generic searches surface whatever sells in volume (budget brands). The actually-high-commission segment (premium ergonomic brands, ¥100,000+ chairs, 1,000-11,000円 commission) didn't show up at all until brand names (エルゴヒューマン/オカムラ/ハーマンミラー) were added as their own queries — those listings often don't even contain generic terms like "オフィスチェア" in their title, so the brand names also need to go into `requiredKeywords` as OR alternatives. A category can have both a low-commission mass-market segment and a high-commission premium segment that generic terms miss entirely.

## Step 1 — Sample live data before writing any config

This is the step that's easiest to skip and most important not to. Write a short throwaway Node script (see `scripts/sample_category.cjs` in this skill for a ready-made version — pass it your queries) that:
1. Reads `YAHOO_APP_ID` from `.dev.vars` in the project root.
2. Calls `https://shopping.yahooapis.jp/ShoppingWebService/V3/itemSearch` for each query with `results=50&in_stock=true&condition=new` (no delivery params needed for this sampling pass).
3. Prints, across all hits: the distribution of `price * affiliateRate / 100` (this is the estimated commission) — you need the **median** and the **max**.
4. Prints any hits whose `description` or `headLine` contains lead-time language (`お取り寄せ`, `取り寄せ`, `予約`, `入荷`, `受注生産`) so you know these need excluding.
5. Prints a sample of hit `name` fields so you can judge whether your required-keyword is too loose (irrelevant products slipping in) or too strict (nothing matches).

After the first sample, run `scripts/check_filters.cjs` with your draft `--queries` / `--required` / `--exclude`. It prints, per exclude keyword, how many products it removed plus sample names, so you can see **false exclusions of genuine products** and **leftover accessories/consumables** before writing any config. Run it again after every change to the exclude list (mind the 30 req/min rate limit: queries × pages ≤ 10 per run, wait about a minute between runs).

**Exclude keywords must never be a substring of an ordinary word.** Two real incidents: `ラック` (meant for "プリンターラック") also matched the colour name `ブラック` and silently removed most black printers; `インク` can't be used alone because `インクジェット` contains it. Use the specific phrase (`プリンターラック`, `収納ラック`) instead. A keyword that accounts for a large share of the exclusions is the first suspect — the script flags those.

**Never exclude on an attribute word that genuine products also carry in their names.** Sellers stuff search words into product names, so a word that "sounds like" another product type often appears on the genuine main unit. Each of these removed real products in testing and was dropped from the exclude list: `本棚` (steel file cabinets are titled "書庫 本棚 書棚"), `勉強机`/`学習机` (corporate steel desks carry them), `ゲーミング` (FlexiSpot standing desks), `配線` ("配線穴" on desks), `モニター台` ("モニター台付き" desks), `お絵かき`/`子供` (whiteboards titled "…会議 お絵かき メニューボード"), `マーカー` ("マーカー付き"), `デスク` (matches "デスクトップ" tabletop boards), `リビング`. Prefer the specific phrase (`お絵描きボード`, `デスクマット`, `カーブ型天板`, `ホワイトボードシート`). Decide by reading the per-keyword samples `check_filters.cjs` prints: if a sample is a genuine product, drop or narrow that keyword. For a stray item that shares its words with real products (e.g. a single-unit marker priced at a few hundred yen), rely on `minEstimatedCommission` instead of an exclude word.

**Query order matters.** `fetchCandidates` stops fetching further queries as soon as it has `targetCount` candidates, so a later query may never run. For printers, putting the generic `複合機`/`プリンター` first filled the pool with inkjet models and the business-oriented `レーザー複合機` query never ran; putting `レーザー複合機` first fixed the mix. Put the segment you must not lose first, or raise `candidatesTargetCount` (see Step 2). Also expect the final count to be far below the fetched count: `dedupeByJan` / `dedupeByExactName` collapse the same product listed by many stores (shredder: 170 after exclusion → 62 final).

**Pick queries that target the product body, not the consumables.** A bare `プリンター` has ~700k hits dominated by ink, paper and labels. Prefer words that only appear on the main product (`複合機`, `レーザー複合機`) and filter the rest with exclude keywords.

**Measure the real numbers with `scripts/measure_candidates.cjs`** before fixing `searchQueries`, `candidatesTargetCount` and `minEstimatedCommission`. It runs the production `fetchCandidates` for Tokyo (`area=13`, up to 翌々日) for every combination of `--target` and `--min`, and prints final count, the share arriving tomorrow, API calls per cache miss, the commission distribution and the top-commission products. Use `--tag "<regex>"` to see the balance when one category merges two kinds of product (e.g. 書庫 vs デスク). Findings from today's categories:
- **Merged categories need the smaller side first.** Office desk + steel cabinet: with `オフィスデスク` first and target 100, desks filled the pool and cabinets were 1-5 items; `スチール書庫` first with target 200 gave 106 cabinets / 72 desks. Raise `maxDisplayCount` (100) too, otherwise the returned top-50 leans to one side.
- **API calls per cache miss = queries × up to 3 pages.** 2 queries ≈ 6 calls, 3 queries ≈ 9 (whiteboard with a third query hit the 30/min limit while testing and added little). Keep it to 2 queries unless the third clearly adds items.
- **An outlier can distort `revenueScoreReferenceMax`.** A 65-inch 電子黒板 (¥348,000, commission 3,480円) topped the whiteboard list while normal products peaked near 200円; using 3,480 would have flattened every normal product's revenue score to ~0 (the same bug projector once had). Look at the top-commission names: if it is a different kind of product (electronic board, repair/refresh liquid "復活君", an A-frame sign), exclude it by a specific word and set the reference near the remaining maximum. If it is a genuine main unit (FlexiSpot standing desk, ¥149,000 at 2%), keep it and use the maximum.

**Don't reflexively add qualifier words (法人/業務用/オフィス/ビジネス) to every query.** For `monitor`, queries like "法人 PCモニター"/"業務用 モニター"/"オフィス モニター" shipped initially and produced only ~4 results for Tokyo even though Yahoo's own site shows 10,000+ hits for a plain "PCモニター" search — real monitor listings almost never contain those qualifier words in their product name, so adding them to the query throws away nearly the whole relevant inventory before your own required/exclude filtering ever runs. Sample with both a plain product-name query and a qualifier-added query, and prefer the plain one unless the plain query is so generic it pulls in mostly noise (this was true for `projector`, where "プロジェクター" alone is unambiguous enough that qualifiers weren't the bottleneck — but it's not a safe default to assume).

From this sample, derive:
- **`revenueScoreReferenceMax`**: set it near the observed max commission, not an arbitrary round number. For projector the real distribution was median ~170円/max ~5,200円, and the correct reference max was 3,000 — a naive default of 10,000 made the revenue score useless (see the memory file for the exact bug). Every category's affiliate rate and price range differs, so this number WILL be different for orchids/printers/whatever — never copy projector's `3000` verbatim without sampling.
- **`longLeadTimeExcludeKeywords`**: the standard lead-time exclusions, always the same 7 across every category — `お取り寄せ`, `取り寄せ`, `予約商品`, `入荷次第`, `入荷未定`, `受注生産`, `メーカー取寄`. This is the one field checked against name **and** description (`filterRelevantProducts` in `productFilter.ts`), because these phrases usually only appear in the description.
- **`excludeKeywords`**: accessory/irrelevant-item keywords your sample reveals (for projector: スクリーン, ケース, バッグ, ケーブル, ランプ, リモコン, 交換部品, スタンド, 天吊, 金具, アクセサリー — your category will have its own equivalents, e.g. flower categories might need to exclude 造花/プリザーブド if the user only wants live flowers). **This field is checked against the product name only, never the description** — do not put lead-time phrases here, and don't expect description-level matching. This split exists because checking accessory words against description caused real false exclusions: EPSON's own genuine business projectors got excluded because their spec text says things like "光源:ランプ" or "HDMIケーブル付属", which matched `ランプ`/`ケーブル` even though the product itself isn't a lamp or a cable (2026-09-26 incident, found when the user asked to audit projector's filtering after a similar issue in `monitor`). Accessory products reliably self-identify in their own name (a screen is titled "プロジェクタースクリーン", a replacement lamp "プロジェクター用ランプ"), so name-only matching still catches them without the collateral damage.

## Step 2 — Generate the config file

Create `src/lib/commerce/categories/<slug>.config.ts`. Copy the shape of `src/lib/commerce/categories/projector.config.ts` field-for-field — it implements `CommerceCategoryConfig` from `../types`. Keep these defaults unless the user asks otherwise (they're the result of prior corrections, not arbitrary):

- `weights`: `{ delivery: 0.29, conversionProxy: 0.21, review: 0.12, store: 0.08, revenue: 0.30 }` — revenue was raised to 50% early on, then brought back down to 30% on 2026-09-26 paired with `minEstimatedCommission` (see below) taking over the job of filtering out low-value products, rather than just down-weighting them in the ranking. Keep this ratio unless told to change it again.
- `minEstimatedCommission` (optional): drops any product whose estimated commission (`price * affiliateRate / 100`) is below this yen amount, before it ever reaches the ranking. **Always measure the actual impact per category before setting this** — the same threshold has wildly different effects depending on the category's typical commission level. When this was set to 500円 across all three categories, projector went 34→26 results, orchid to 15, but `monitor` (median commission only ~152円) went 50→9 — nearly gutting the category. Test with the site's normal query pattern (area only, no explicit `delivery` param — this defaults to day≤2 and pulls a much bigger pool than pinning `delivery=1`, which can look deceptively empty).
- Measured results of `minEstimatedCommission` since then: shredder (commission rate ~1%, median 179円) went 62→31 results at 500円, so it uses 200円 (54 results); printer went ~50→20 at 500円, so it also uses 200円 (51). Measure with `fetchCandidates` itself (bundle it with `npx esbuild src/lib/commerce/fetchCandidates.ts --bundle --platform=node --format=esm --outfile=<scratchpad>/fc.mjs`, then call it with the exact config values and `area: "13", deliveryDay: 2`) rather than guessing.
- `candidatesTargetCount` / `maxDisplayCount` (optional, added 2026-09-30): default target is 100 candidates and 50 products returned. Raise them only when a category needs a bigger pool (generator: 200/150, because the STEP filters work on the returned products; printer: target 200 so all three queries run). Cost: each cache miss now makes about 4-5 Yahoo API calls instead of 2, and the cache key is separated per category via a `-t<count>` suffix so other categories' caches aren't invalidated.
- Optional page extras, all off unless set in the config: `popularBrands` (brand cards; use the `add-popular-brand-section` skill), `sponsoredSection` (an explained ad block with a third-party banner; see `commerce-page-design`). Don't add them unless the user asked.
- `sortOptions`: exactly `recommended`(即納おすすめ) / `trust`(売れ筋・安心重視) / `reviewCount`(レビュー件数) / `priceAsc`(価格が安い順). **Do not add a revenue/報酬 sort option** — it was built once and explicitly removed as inappropriate to expose to users.
- No `priceBands` or `reviewThresholds` fields exist in `CommerceCategoryConfig` at all (they were removed from the type, not just unused) — don't reintroduce a price or review filter. Both were tried and explicitly removed: price filtering frequently zeroed out results, and Yahoo!ショッピング's review data is too sparse for a threshold filter to be useful.
- Copy text rules: never write 今日 or 当日 anywhere (H1, meta description, subheadline, FAQ) — same-day arrival isn't realistic via this API and the option doesn't exist in the UI at all. Never mention 収益性/報酬 in any user-facing string (intro, FAQ, disclaimers) — that's internal-only.
- `apiPath` must end with a trailing slash (`/api/<slug>/products/`) — this project has `trailingSlash: "always"` site-wide, and both the route and any `fetch()` call to it need the slash or it 404s.
- Write `seoSections` (2 short sections of genuine buying-advice, no unfounded specific numeric claims) and `faq` (5 items covering: fastest realistic arrival, "明日までに届く商品だけ探せますか", "お届け先によって商品は変わりますか", a category-specific "何を確認すればよいか" question, and "表示されている配送予定は確定ですか") — model these directly on projector's, just re-worded for the new product type.
- **`ads` (the ValueCommerce Yahoo!ショッピング banner) is required, not optional** — copy `pcBannerHtml`/`mobileOverlayHtml` byte-for-byte from `projector.config.ts` into every new category's config. This was missed for 胡蝶蘭 (shipped without it, user caught it later on the live page) — it's the same account/program banner across all categories, not projector-specific, so there's no reason to leave it out. Never edit the tag content itself (ValueCommerce ToS forbids modifying ad code).

## Step 3 — Register the config and create the thin page wrapper

Import the config in `src/lib/commerce/registry.ts` and add it to `configs` (the registry validates required fields at build time). Then create only `src/pages/categories/<slug>/index.astro` by copying `src/pages/categories/monitor/index.astro` — it just renders `<CommerceCategoryPage config={...} />`. **There is no per-category API route**: the dynamic route `src/pages/api/[slug]/products.ts` resolves the config from the registry and calls `handleProductsRequest`. Do not create `src/pages/api/<slug>/products.ts` by copying projector's (the old procedure). **Do not fork or modify `src/components/commerce/CommerceFilterPanel.astro` or `ProductGrid.astro`** — they are category-agnostic by design; pass differences through the config instead. If a new category genuinely needs a UI element neither component has, that's worth a real conversation with the user before hacking around it, not a silent fork.

Key behaviours of the shared handler (`handleProductsRequest.ts` / `fetchCandidates.ts`) — they are all fixes, not stylistic choices, so don't regress them when editing those files:
- `effectiveDeliveryDay = area ? delivery ?? 2 : undefined` — if you drop this, delivery-day info silently stops being populated for most results the moment a prefecture is picked but 到着希望 is left at "指定なし" (Yahoo only fills in `delivery.day` when area+day+deadline are all three present in the request).
- Candidate gathering is `fetchCandidates()` in `src/lib/commerce/fetchCandidates.ts` (2026-09-27 rewrite, replacing the old `yahooShoppingClient.ts`/`searchProducts`). It does, per category, in this exact order: (1) fetch pages from Yahoo (`results=100` per page — confirmed empirically to be the real API cap, `results=200` returns HTTP 400; paginate via `start` up to `maxPagesPerQuery` per query, stopping early once enough candidates are found), (2) normalize + dedupe by `code` across pages/queries as they stream in, (3) `requiredKeywords`, (4) `excludeKeywords`, (5) `longLeadTimeExcludeKeywords`, (6) compute `estimatedCommission` per item, (7) drop anything below `minEstimatedCommission`, (8) `dedupeByJan` + `dedupeByExactName`, (9) slice to `targetCount` (100). **No commission-based sort happens here** — Yahoo's own relevance order is preserved throughout; only the final user-selected 並び順 (applied afterward in `handleProductsRequest.ts`) reorders anything.
- **Only request one `delivery_day` value, never both 1 and 2 separately.** Empirically confirmed (2026-09-27): requesting `delivery_day=2` returns a strict superset of what `delivery_day=1` returns (every day=1 hit also appeared in the day=2 response, plus more) — Yahoo's own semantics for this parameter are "arrives within N days," not "arrives in exactly N days." The old code fetched both and merged them, which was pure waste (double the API calls for identical coverage). Just pass the resolved `effectiveDeliveryDay` straight through as a single value.
- `filterRelevantProducts` (in `productFilter.ts`, still used internally by `fetchCandidates`) checks `requiredKeywords`/`excludeKeywords` against **name only**, and `longLeadTimeExcludeKeywords` against **name AND description** — long-lead-time disclosures usually only appear in the description field, never the name, but accessory-type `excludeKeywords` must stay name-only (see Step 2 above for why).
- `fetchCandidates` throws if **any** page fetch fails (not just if all of them do) — same principle as the old `searchProducts`, carried forward. This was a real production incident on 2026-09-26: during heavy manual testing that quietly tripped Yahoo's rate limit (30 req/min per app ID), only a couple of sub-requests would succeed, and "throw only if all failed" treated that tiny, biased partial result as a normal successful fetch — which then got cached as the candidate pool for the full TTL, making pages show almost nothing. Don't loosen this — a failed fetch should fall through to `handleProductsRequest.ts`'s 24-hour fallback cache (last known-good complete result) instead of silently caching a degraded partial one.
- Cloudflare Cache API caching at 30 minutes, keyed only by `{area, effectiveDelivery}` — **not** `sort`, since sort never affects what gets fetched from Yahoo, only how the already-fetched candidates (now cached as the post-`fetchCandidates` scored list) are ordered. Remember this means a code change to your ranking/fetch logic won't show up in local `wrangler dev` testing for a param combo you've already hit, until you delete `.wrangler/state/v3/cache` or use a never-before-used param combination.
- **Test result counts with the site's default param shape** (`?area=13`, no explicit `delivery`) rather than pinning `delivery=1` — the latter only queries Yahoo for day=1 confirmations specifically and can look deceptively close to empty for categories where few sellers guarantee next-day delivery, even though the category has plenty of inventory once day=2 is also allowed (which is what happens by default when a user just picks a prefecture).
- Yahoo's own consumer site has a "優良配送" (certified/quality delivery) store badge and filter — **this is not exposed anywhere in the public itemSearch v3 API** (confirmed by reading the complete official parameter table directly, not a summary). Don't assume it can be replicated; the `delivery_area`/`delivery_day`/`delivery_deadline` mechanism this site uses is a different, API-accessible signal (Yahoo's own per-item computation of "can this reach this prefecture in N days if ordered now"), not the same thing as the badge.

## Step 4 — Wire it into navigation

- Add an entry to `commerceCategories` in `src/data/site-nav.ts` (name, href `/categories/<slug>/`, a short speed label like `最短翌日〜翌々日`).
- `sitemap.xml.ts` derives commerce category paths from the registry automatically (as of 2026-09-26) — no change needed there.
- `src/pages/categories/index.astro` and `src/pages/index.astro` already render `commerceCategories` generically — no changes needed there, they'll pick up the new entry automatically.
- Add one line for the new page to `public/llms.txt` (CLAUDE.md's SEO rule: every new category/page must be listed there; state that the delivery date is not guaranteed).
- If the user wants homepage entry points beyond the category grid (人気キーワード chip, 急ぎの目的から探す item, 部署から探す item — projector got all of these), add them to the relevant arrays in `site-nav.ts` too, following projector's phrasing style (always mentioning "明日" as the fastest realistic promise, never "今日").

## Step 5 — Verify before asking to deploy

1. `npm run build`. On Windows, if you hit `EPERM ... dist\_worker.js`, a leftover `wrangler dev`/`workerd.exe` process is holding a lock — run `taskkill //F //IM wrangler.exe` and `taskkill //F //IM workerd.exe` (plain `pkill` from Git Bash doesn't reliably match these process names), then rebuild.
2. Run `wrangler dev` locally and hit `/api/<slug>/products/?area=13` (Tokyo) — confirm real products come back, confirm most have `deliveryDay: 1` (not `null`), and skim names for anything the required/exclude keywords should have caught but didn't.
3. Grep the built HTML for `今日` and `当日` and `収益性`/`報酬` — none should appear anywhere on the new page.
4. **Verify GA4/LINEヤフー広告 measurement fires — no tag installation needed, but confirm it actually works** (2026-09-28 rule, see CLAUDE.md's commerce-rules section and `docs/new-category-checklist.md` step 7). GA4 and the LINEヤフー広告 Yahoo!タグ are both installed once, site-wide, in `Layout.astro`; `outbound_product_click`/`brand_click`/`filter_use` tracking code lives in the shared `ProductGrid.astro`/`PickupBrandSection.astro`/`CommerceFilterPanel.astro` components and keys off the `slug` each already receives — so a new category gets tracking automatically as long as it uses those shared components normally, with no separate tag-installation step. Still verify in a browser console before shipping: click a product card CTA and confirm `window.dataLayer` gained exactly one `outbound_product_click` entry with the new category's slug as `category`; if `popularBrands` is set, confirm a brand card click adds both `outbound_product_click` and `brand_click`; confirm changing お届け先/到着希望/並び順 or clicking 商品を探す adds `filter_use`; confirm no new console errors; confirm the clicked link's `href` is already LinkSwitch-converted (`dalr.valuecommerce.com/...`) at click time.
5. Run `npm run test` (the snapshot test covers only projector, so it proves the shared template is unchanged) and `npm run build`. Do not run `wrangler deploy` on your own initiative: report the result and wait. ## Working environment notes (Windows, Claude Code)

- `python` is not available in this environment (the call silently does nothing and a later check shows the file unchanged). Patch files with the Edit tool or a small `node` script; preserve CRLF line endings if the file has them.
- Tool pitfalls seen repeatedly (details in the `windows-claude-code-workflow` skill): long `sleep` commands are blocked (use Monitor, or do other work while a rate limit clears); a bash heredoc containing quotes/backticks/`$` can fail to parse — write the script with the Write tool and run it with node; `String.replace(a, b)` treats `$` in `b` specially, so pass `() => b`.
- Never run `git stash`, `git checkout .` or similar to "compare before/after" — the working tree contains a lot of uncommitted work. Compare against a copy of the file instead.
- For a local check, start the dev server with the `astro-dev` entry in `.claude/launch.json` (`preview_start`); wait ~10 seconds for it to listen before navigating. Stop it afterwards.
- The `ProductGrid.astro` inline script text is part of `body.textContent`, so any change to it makes the projector snapshot's `bodyText` differ. Check that the diff is only the intended script text and the other snapshot keys are identical, then regenerate with `node tests/support/captureSnapshot.mjs dist/categories/projector/index.html tests/__snapshots__/projector.snapshot.json`.

## Watch out for "関連Word" keyword-stuffing in descriptions

Many Yahoo!ショッピング sellers append a giant list of unrelated search terms to the end of their product description (e.g. `関連Word: ... モニターアーム 壁掛け ...`) purely for their own internal search matching — this is not describing the actual product. This mainly matters for `longLeadTimeExcludeKeywords` (the one field still checked against description) — a genuine product could get wrongly excluded just because the seller's SEO tag-list happens to mention a lead-time-sounding word. `productFilter.ts` strips everything from `関連Word:`/`関連ワード:`/`関連キーワード:`/`検索ワード:` onward before running that check, so this is handled automatically for every category — but if you ever see a plausible-looking product missing for no obvious reason, fetch its raw `description` from the API and check for one of these markers before assuming your keyword lists themselves are at fault.
